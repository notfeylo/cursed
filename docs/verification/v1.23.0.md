# v1.23.0 — verification record

What was checked, what was not, and what could not be. Written to the standard
in `README.md` in this directory.

Machine: Windows 11 Home, build 26200, x64, 24 logical processors. One machine,
which is where most of the gaps at the bottom come from — and this release is
the one where that finally cost something, so the gap list is worth reading
before the results.

## The bug a second machine found

**Photo mode had never run on a PC without developer tools on it.** v1.22.0's
record listed "photo mode on ARM64 or 32-bit" as unverified and said only the
x64 runtime had been loaded and run. What it did not say — because nobody had
thought to doubt it — was that the x64 runtime had only ever been loaded on
*this* machine, and machines like this one are not representative.

Every published `onnxruntime` build statically imports `MSVCP140.dll`,
`MSVCP140_1.dll` and `VCRUNTIME140.dll`, plus `VCRUNTIME140_1.dll` on x64. That
is the Visual C++ redistributable, and Windows does not include it. Read out of
the import tables rather than from memory:

| Binary | Imports the C++ runtime? |
| --- | --- |
| `Cursed.exe` | **no** — OS DLLs and the UCRT only |
| `onnxruntime-x64.dll` | `MSVCP140`, `MSVCP140_1`, `VCRUNTIME140`, `VCRUNTIME140_1` |
| `onnxruntime-arm64.dll` | `MSVCP140`, `MSVCP140_1`, `VCRUNTIME140` |
| `onnxruntime-x86.dll` | `MSVCP140`, `MSVCP140_1`, `VCRUNTIME140` |

Rust links the MSVC C runtime statically, so the app runs anywhere and the one
feature that reaches for something else does not. That is why it presented as
"the app works, photo mode is broken" and why every machine here hid it.

## Photo mode: the C++ runtime, measured

The fix rests on one claim — that loading our verified copy by absolute path
first binds the process's `msvcp140.dll` to *that* file, so the runtime's import
resolves without a search. `libloading` calls `LoadLibraryExW(path, NULL, 0)`
with no `LOAD_WITH_ALTERED_SEARCH_PATH`, so a file sitting next to
`onnxruntime-x64.dll` would **not** be found; the preload is what does the work.

| Check | Result |
| --- | --- |
| `a_preloaded_runtime_is_the_copy_that_gets_used` | `GetModuleFileNameW` reports `%APPDATA%\Cursed\models\msvcp140.dll`, not System32 |
| The end-to-end model test, against those copies | passes; the matte is unchanged |
| Dependency closure per architecture | taken from each published runtime's import table, not assumed |

## Photo mode: the memory, measured

Committed private bytes, release build, on 24 logical processors.

| | before | after |
| --- | --- | --- |
| Committed after one cutout | **554 MB** | **26 MB** |
| Still committed afterwards | 554 MB | ~0 MB |
| Resting footprint after a cut | 557 MB | 27 MB |
| Inference | 91 ms | 102 ms |

Attributed step by step: loading the DLL cost 1 MB, building the session 25 MB,
and **the first `run` committed the remaining ~530 MB** — the arena allocator,
which sizes itself to the graph and not to the picture, so a 64x64 image cost
exactly what a 19-megapixel one did. `release()` returned all of it, which is
what proved the session owned it. `with_memory_pattern(false)` and
`with_intra_threads(1/2/4)` each changed it by less than 20 MB; disabling the
CPU arena is what moved it.

Eight consecutive cutouts of a 3.7-megapixel picture now sit flat at 27 MB at
rest and 41 MB during, and a 19-megapixel one peaks at 100 MB rather than 896.

**This is the most likely cause of the reported crash**, and it is worth being
plain that it is not confirmed: Rust aborts on a failed allocation and an abort
never reaches the panic hook, so an out-of-memory death leaves nothing in
`cursed.log`. The reporter's machine was a VM, the symptom was the app closing
after three or four cutouts with no message, and one session pinned 554 MB. That
fits. It has not been reproduced on the machine that reported it.

## Not verified

- **The C++ runtime fix, on a machine that lacks the runtime.** This is the one
  that matters. The mechanism is proven here and the diagnosis is proven from
  the import tables, but the actual failing PC has not yet run a build with the
  fix in it. Until it has, this is a well-evidenced fix rather than a confirmed
  one.
- **The crash.** Not reproduced, not confirmed; see above. `cursed.log` from the
  machine that crashed has not been read.
- **ARM64 and 32-bit on real hardware of those architectures.** Still only the
  PE machine type is checked. Photo mode on those architectures has still never
  been loaded, and their C++ runtime sets have been derived from import tables
  rather than exercised.
- **An N → N+1 update on a clean VM.** Unchanged and still the largest
  process gap. §2.5 of the update brief remains open.
- **A long soak.** Three minutes, as in v1.22.0 — not the 24 hours the bare
  `npm run soak` defaults to. Nothing here has been left running overnight.
- **The installer-launch failure path**, and **the Windows 1803 floor** —
  unchanged from v1.22.0.
- **Photo mode over an animation.** Still one inference per frame, still untimed
  on a long source, still no progress shown while it runs. Carried forward again.
- **32-bit photo mode may need more than Windows 1803.** `onnxruntime-x86.dll`
  (ONNX Runtime 1.22.0) statically imports `dxcore.dll`, which the x64 and ARM64
  builds do not. That file is not present on every Windows the app claims to
  support. Noted rather than fixed: nothing has ever run photo mode on 32-bit.
