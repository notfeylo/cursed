in `README.md` in this directory.

the gaps at the bottom come from.

## The update-mode guard, on the real installer

The fault fixed in `a15be2a` is the one worth exercising against the built
artifact rather than a unit test, because it is the installer's own control flow
that was wrong. Installed `Cursed_1.18.0_x64-setup.exe` silently over a running
1.18.0:

- Exit code 0.
- `%APPDATA%\Cursed` unchanged: 2909 files, 19 custom cursors, `applied.json`,
  `presets.json`, `settings.json` and `backup\original_scheme.json` all present.
- `HKCU\Control Panel\Cursors` **identical before and after**, compared by
  exporting the key both times and diffing the export.

The comparison is done with `reg export` and not `Get-ItemProperty` on purpose.
`Get-ItemProperty` expands `REG_EXPAND_SZ`, which is what produced fifteen
confident false failures during the 1.17.0 gate — it compared an expanded
`C:\WINDOWS\cursors\...` against a stored `%SystemRoot%\cursors\...` and called
a byte-perfect restore broken.

User data was backed up before the cycle — everything except `cache` and
`updates`, 446 files and 47.9 MB — along with the cursor registry key. Nothing
had to be restored from it.

## Not verified

- **The full uninstall gate (`scripts/verify-uninstall.ps1`) was not re-run for
  this build.** It was run twice in full at 1.17.0, exit 0, zero residue, and
  nothing in this release touches the uninstall path except the update-mode
  guard — which *was* exercised, above. That is a reason it is likely fine and
  not evidence that it is. It needs a real install-and-remove cycle on a machine
  whose data can be discarded, and the machine available holds 19 custom cursors
  and 2909 files of live user data.
- **The 1.17.0 → 1.18.0 in-app update itself.** Tauri runs the *previous*
  version's uninstaller with `/UPDATE`, so this specific transition runs
  1.17.0's unguarded hooks no matter what ships here: the stock Windows pointer
  is restored and a dialog offers to delete presets and custom cursors,
  defaulting to removing them. No release can fix its own predecessor. It is
  written into the release notes with the advice to install over the top by
  hand instead, and every update from 1.18.0 onward is guarded.
- **ARM64 and 32-bit installers on real hardware of those architectures.** Only
  the PE machine type was checked. The binaries are the right architecture and
  the code compiles and lints clean for each, but nothing has *run* on an ARM64
  or 32-bit Windows.
- **A machine with no WebView2 runtime.** Both the `downloadBootstrapper` path
  and the offline installer remain unexercised against a machine that genuinely
  lacks the runtime.
- **The Windows version guard's refusal path.** It passes on build 26200; it has
  never been seen to *stop* an install.
- **The uninstaller's "keep my presets" branch.** Unchanged and still uncovered —
  a silent uninstall cannot answer a dialog.
- **A fresh install receiving all 36 packs.** The two faults behind 29-of-36
  were found and fixed in `0e9973d` and are covered by tests, but the machine
  here already had the packs, so what was confirmed this cycle is that an
  install over an existing one leaves the catalog at 1 + 36, not that a machine
  which has never seen the app arrives at 36.
- **The §9 clean-VM gate**: DPI scaling 100–200%, reboot persistence, autostart
  returning to the tray, offline behaviour, idle CPU and RAM. Windows Sandbox
  needs Pro and this is Home; the VirtualBox route has not been set up.

## Judgement calls

**Shipping without re-running the uninstall gate.** The alternative was to
uninstall a live install holding real user data on the only machine available,
on the strength of a backup taken minutes earlier. The gate's value is in
catching residue left by *changes to the uninstall path*, and this release makes
exactly one such change, in the direction of doing less. Recorded as not run
rather than reasoned into a pass.

**The 1.17.0 → 1.18.0 update hazard is documented, not worked around.** It could
in principle be softened by shipping a build that refuses to update itself, but
that trades a one-time prompt for a permanent mechanism, and the prompt is
survivable: it asks before deleting, and answering "keep" leaves everything
where it is.

**`CURSED_COMMIT` is unset in release builds**, so an installed release reports
its commit as `local` in the diagnostics. Cosmetic, unchanged since 1.13.0, and
noted here so the next person reading a diagnostic dump does not take it for a
sign that a user is running an unofficial build.
