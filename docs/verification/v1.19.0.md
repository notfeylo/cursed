## The import path, which is what this release is

Everything user-visible here happens between a dropped photograph and a built
cursor, and all three fixes are pinned by tests rather than by looking at the
result and agreeing it seems better.

- **Linear light.** `downscaling_averages_light_and_not_encoded_values` is one
  measurement: a 50% black-and-white checker must resolve to ~188, and the old
  code gives ~128. That single number is the whole bug — every edge in a
  photograph is that checker in miniature.
- **The cut.** Nine cases across `build::matte`, and the two that matter for
  what changed here are `clumps_of_leftover_background_are_swept_up` and
  `a_single_faint_pixel_with_nothing_around_it_is_dust`, held honest by
  `a_detached_detail_that_is_not_the_background_colour_survives` and
  `an_enclosed_colour_that_only_resembles_the_background_survives` — a sweep
  that also removes the dot of an i is not a fix.
- **EXIF orientation.** This had **no test at all** when the gate started, which
  is why the two in `f5042b6` exist. `image` writes no EXIF, so the test
  assembles a tagged JPEG — an APP1 segment behind the SOI holding a TIFF block
  with tag 0x0112 — and asserts that orientation 6 swaps the axes and moves the
  dark half to the right, and that an untagged file comes through exactly as
  stored. Written during this gate and counted in the 201.

The installers were rebuilt after that commit so the published artifacts come
from the tagged tree, not from one two commits behind it.

## Reinstalled over live user data

Twice. First the build made before the test commit, over a running 1.18.0 — the
version transition — and then the artifact that is actually published, over
that. The second run is the one that says the file people download works; the
first is the one that says an upgrade from 1.18.0 keeps their data.

- Exit code 0 both times, and the uninstall entry reads 1.19.0 afterwards.
- `%APPDATA%\Cursed` unchanged: 2913 files, 450 outside `cache` and `updates`,
  20 custom cursors, and `applied.json`, `presets.json`, `settings.json` and
  `backup\original_scheme.json` all present.
- `HKCU\Control Panel\Cursors` **identical before and after**, compared by
  exporting the key both times and diffing the export, on both runs.

The comparison uses `reg export` and not `Get-ItemProperty` on purpose.
`Get-ItemProperty` expands `REG_EXPAND_SZ`, which produced fifteen confident
false failures during the 1.17.0 gate — it compared an expanded
`C:\WINDOWS\cursors\...` against a stored `%SystemRoot%\cursors\...` and called
a byte-perfect restore broken.

This release changes nothing in the installer, so the update-mode guard was not
the point of the exercise; user data surviving an install-over was.

User data was backed up before the cycle — everything except `cache` and
`updates`, 450 files and 49.7 MB — along with the cursor registry key. Nothing
had to be restored from it.

## Not verified

- **A photograph actually imported through the running app.** The three import
  fixes are covered by unit tests over the same functions the app calls, and the
  installed build launches and reads its catalog, but no image was dragged into
  the built 1.19.0 and inspected by eye. The import path is driven from the UI
  and there is no headless entry point to it.
- **The timing claims.** 18.2 s → 3.2 s for a 19 MP photograph and 5.2 s → 1.0 s
  for a 5 MP one were measured when the cap was written, in `951ad09`, and are
  repeated in the release notes rather than re-measured here.
- **PNG carrying an EXIF orientation tag.** The tag is read on the general
  decode path, which JPEG, WebP and BMP take; `decode_png` does not consult it.
  Phones write JPEG and screenshots have no orientation tag, so this is a real
  gap and a narrow one — a PNG exported from a camera workflow with a rotation
  tag would still come in sideways.
- **The full uninstall gate (`scripts/verify-uninstall.ps1`).** Not re-run, for
  the same reason as at 1.18.0: it needs a machine whose data can be discarded,
  and this one holds 20 custom cursors and 2913 files of live user data. Nothing
  in this release touches the uninstall path.
- **ARM64 and 32-bit installers on real hardware of those architectures.** Only
  the PE machine type was checked. The binaries are the right architecture and
  the code compiles and lints clean for each, but nothing has *run* on an ARM64
  or 32-bit Windows.
- **A machine with no WebView2 runtime.** Both the `downloadBootstrapper` path
  and the offline installer remain unexercised against a machine that genuinely
  lacks the runtime.
- **The Windows version guard's refusal path.** It passes on build 26200; it has
  never been seen to *stop* an install.
- **A fresh install receiving all 36 packs.** The machine here already had them,
  so what was confirmed is that an install over an existing one leaves the
  catalog at 1 + 36.
- **The §9 clean-VM gate**: DPI scaling 100–200%, reboot persistence, autostart
  returning to the tray, offline behaviour, idle CPU and RAM. Windows Sandbox
  needs Pro and this is Home; the VirtualBox route has not been set up.

## Judgement calls

**A test was written during the gate rather than after the release.** Finding
that the headline fix had nothing behind it is a reason to stop and write one,
not a reason to note the gap and ship. It cost one commit and a rebuild, and the
alternative was a release whose main claim rested on three lines and a code
review.

**`cargo fmt --check` is not part of the gate and was not run as one.** Every
file in `src-tauri/src` differs from rustfmt's output; the code is wrapped by
hand around its comments. Running it would reformat 27 files and hide the
release in the diff. Recorded here so the next person who runs it does not read
the output as rot.

**The timings were not re-measured.** They were taken on this machine two
commits ago against the same code, and a re-measurement would confirm the
machine rather than the change. Repeating a number is not the same as verifying
it, which is why it is listed above instead.

**`CURSED_COMMIT` is unset in release builds**, so an installed release reports
its commit as `local` in the diagnostics — visible in the launch line quoted
above. Cosmetic, unchanged since 1.13.0, and noted so the next person reading a
diagnostic dump does not take it for a sign of an unofficial build.
