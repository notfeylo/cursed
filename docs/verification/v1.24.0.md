# v1.24.0 — verification record

What was checked, what was not, and what could not be. Written to the standard
in `README.md` in this directory.

Machine: Windows 11 Home, build 26200, x64, 24 logical processors.

## What this release is, and what it is not

It was reported as "the quality got worse recently, and the force-pushes to
GitHub probably did it". **The force-pushes could not have done it, and that was
checked before anything else.** They landed on three Dependabot branches and on
`website/`. Nothing was merged to `main`, no tag was cut, and no release was
published between v1.23.0 and this one — so the binary on the reporting machine
was built from tag `v1.23.0` at `514803b`, which predates all of it.

Both defects are real, both are older than the report, and neither is a
regression. The first shipped with photo mode. The second has been in the size
ladder since it was written.

## The halo

**Claim:** photo mode left the background's colour in every partly-transparent
pixel, so a cut-out had a grey rim that only showed against a light backdrop.

**Evidence, not inference.** `remove_background_learned` wrote
`[r, g, b, combined]` — the original RGB with a new alpha — and there was no
unmix anywhere on that path. `matte::unblend` has existed for the keyed path
since it grew a soft edge; the learned path never called it.

**Ruled out first**, because each would have produced a similar-looking rim and
each was cheaper to believe:

| Suspect | How it was ruled out |
| --- | --- |
| Premultiplied alpha written into the `.cur` | Decoded a cached `Arrow.cur` and read the 32 px entry: 109 pixels at partial alpha, 96 of them with `max(RGB) > A`, ratios up to 127×. Straight alpha, which is correct. |
| A bad AND mask | `cur_writer` sets the bit only where alpha is exactly 0, and the file's mask matches. |
| Non-premultiplied resize darkening edges | `Bitmap::resized` is Lanczos3 in linear light with premultiplied alpha; `sharpened` is premultiplied too. |
| Frames missing from the file | The same cached cursor carries all eight rungs it was built with. |

**Fixed** by averaging the local backdrop from cleared pixels within four and
undoing the blend against it. Pixels with fewer than three cleared neighbours
are left untouched: unmixing against a guess is worse than not unmixing.

**Tested** by `photo::decontamination_tests` — a 50%-covered red fringe over
black comes back the subject's colour with its coverage unchanged, opaque and
cleared pixels are byte-identical, and a fringe with no background near it is
left as it arrived.

**Corrected after the first draft of this record.** It said the end-to-end test
was `#[ignore]`d. It is not, and the `#[ignore]` in that file is on
`a_learned_matte_gives_its_memory_back`, which is skipped for an unrelated
reason — it reads process-wide committed bytes and the rest of the suite
allocates around it.

`the_model_produces_a_matte_when_it_is_installed` runs the real model through
the real runtime whenever both files are on the machine, and both are on this
one (`%APPDATA%\Cursed\models`), so it ran. It now also asserts the unmix: the
mean red of the soft band must come out **strictly** brighter than the same
pixels in the source, on a fixture whose subject is light and whose backdrop is
dark.

Strictly, because decontamination leaves RGB untouched when it does nothing —
a `>=` assertion is satisfied by the bug it is meant to catch. That was verified
by removing the call and re-running: the soft band holds at 131 across 1705
pixels and the test fails, which is what it should do.

**Still not verified:** the whole thing on a real photograph rather than a
generated one. A photograph cannot become a fixture here, and the blocker is not
the licence — it is that the model and runtime are a 20 MB download nothing in
the build fetches, so the test skips on any clean checkout and in CI regardless
of what image sits beside it. Committing a photo would add weight and change
nothing about where the test runs. The skip now prints `SKIPPED` rather than
returning silently, so a machine without the artifacts says so instead of
looking like a pass.

## The blocky large pointer

**Claim:** `TARGET_SIZES` stopped at 128 px while `CursorBaseSize` goes to 256.

**Confirmed in the code, both ends.** `scheme::write_base_size` clamps to
`32..=256` and `presets` does the same; the app's own slider maxes at 128, which
is why this was invisible to anyone who set their pointer size here rather than
in Windows' accessibility settings. Above 128 px the shell was stretching our
largest bitmap.

**Fixed** by adding 192 and 256 to the ladder. Three assertions failed on the
change and all three were assertions about the old top rung, not about
behaviour: `nearest_size(1000)` now lands on 256, a built `.cur` carries ten
entries, and an animation asked for at 200 px shrinks the 256 px rung instead of
stretching the 128 px one. That last one is the fix stating itself.

**Not verified:** what this looks like at an accessibility pointer size on a
real machine. The pointer size on this one has never been moved off the default,
which is the reason the defect survived this long. That check is now written
into the standing gate in `README.md` beside this file, along with the
light-background check that would have caught the halo, so both are looked at
every release rather than rediscovered.

## What was not checked, again

Unchanged from v1.23.0 and still true:

- **ARM64 and 32-bit installers on real hardware.** Only the PE machine type is
  ever confirmed. This release changes the size ladder, which is architecture-
  independent, so the risk is no worse than it was — but it is not lower either.
- **An N → N+1 update on a clean VM.** Still never run.
- **The uninstall gate** (`verify-uninstall.ps1`) needs a machine to be rolled
  back afterwards and was not run for this release.
- **Cache growth in the field.** The two new rungs roughly quadruple a cached
  cursor's bytes, measured from the format rather than from a populated cache on
  a machine that has applied many packs. Whether that is a number anybody
  notices is unknown.
- **First-apply time with ten rungs instead of eight.** The 192 px and 256 px
  renders are the two most expensive, and no timing was taken.
