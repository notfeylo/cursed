# v1.25.0 — verification record

What was checked, what was not, and what could not be. Written to the standard
in `README.md` in this directory.

Machine: Windows 11 Home, build 26200, x64, 24 logical processors.

## How this one was found, because the method is the point

v1.24.0 shipped two fixes for "the cursors look bad" and the pointer still
looked bad. The first two were found by reading code and reasoning about it.
This one was found by **measuring the artifact on the machine that had the
problem**, which is what should have happened first.

What the measurements said, in order:

| Measured | Result | What it ruled out |
| --- | --- | --- |
| `applied.json` | `size: 38`, outline on, user pack | — |
| The applied `.cur`'s directory | rungs `[10, 16, 24, 32, 48, 64, 96, 128]` | **No 38 px entry exists.** |
| `source.png` beside it | 977×977, RGBA | Not an upscale of a small source |
| The 32 px entry's alpha | 443 clear, 147 opaque, 434 soft | Alpha is graded, not binary — the matte is not the fault |
| A cached catalog `.cur` | straight alpha, `max(RGB) > A` on 96 of 109 soft pixels | Not premultiplication |

The picture only has one reading left: Windows was handed a 32 px cursor and
asked for 38, and scaled it. Its scale is bilinear, unpremultiplied and not
gamma corrected, and a 1.19× enlargement of an outlined 32 px glyph is exactly
the soft, stepped, "I can see the pixels" pointer that was reported.

## The size of the defect

The slider ran 10 to 128 in twos. Sixty positions, ten rungs, **fifty-two of
which had no exact entry**. The eight that did are the preset chips drawn
directly underneath it — so the app contained its own control group, and nobody
noticed because the people who click presets never saw the bug and the people
who drag never saw it work.

`packs/catalog.rs` had already diagnosed this failure once, for `.ani`, and its
comment ends "while the static cursor beside it stayed sharp". That clause is
false and had been since it was written.

## The fix, and why it is in three places

A size can arrive three ways, and snapping only one of them leaves the other two
broken:

- `Settings::sanitised` — what the app is told to use, including a hand-edited
  file, a preset restored from a `.cfpack`, and a value written by an older
  build.
- `effective_size` — what the app inherits when it is told nothing and reads
  `CursorBaseSize`, which is where Windows' accessibility pointer-size slider
  puts its answer.
- The control itself, now discrete over the ladder. Snapping only in the backend
  would have displayed 38 px while drawing 32.

**Rejected:** adding the asked-for size to the ladder as an extra rung. It is
sharper still, and it requires keying the static render cache by size — which
was tried, and left 150 near-identical directories and 395 MB in one pack's
cache because dragging the slider wrote a fresh copy at every pixel. Snapping
puts the same pixels on screen for none of that cost. Recorded here so it is not
proposed again without that history.

## The gate

| Check | Result |
| --- | --- |
| `cargo clippy --all-targets -- -D warnings` | pass |
| the same on `aarch64-pc-windows-msvc` | pass |
| the same on `i686-pc-windows-msvc` | pass |
| `cargo clippy --features dev-channel -- -D warnings` | pass |
| `cargo test` | 356 pass, 0 fail, 1 ignored |
| `cargo test --features dev-channel` | 356 pass, 0 fail, 1 ignored |
| `npx tsc --noEmit` | pass |
| `npm run build` | pass |
| `npm run check:bundle` | pass |

Two tests are new and both would have caught this: every size in
`MIN_CURSOR_PX..=MAX_CURSOR_PX` must come out of `effective_size` as a member of
`TARGET_SIZES`, and 38, 78 and 120 specifically must land on 32, 64 and 128. The
first is the general statement; the second names the number off the machine that
reported it, so a regression says so in the failure message.

## Not verified

- **The pointer on a screen at each rung.** This is the check
  `README.md` beside this file added last release, and it still has not been
  performed — the fix is reasoned from the file format and confirmed by the
  absent directory entry, not by looking. That gap is now two releases old and
  is the single most valuable thing anyone could do to this project.
- **The uninstall gate**, which needs a machine to roll back afterwards.
- **ARM64 and 32-bit on real hardware**, and **an N → N+1 update on a clean
  VM** — both unchanged and both still never run.
- **Whether a user notices their pointer changing size on update.** A size that
  was not a rung moves to the nearest one; 38 becomes 32. That is a visible
  change to something the user chose, and no upgrade path softens it or explains
  it in the app. The changelog says so; the app does not.
