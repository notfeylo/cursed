## The bug this release is about, and how it was actually found

The complaint was that updates do nothing: a button that never moves, a download
that fails its checksum every time, an app insisting it is current. Three
symptoms, and the temptation is to chase three causes.

The first hypothesis was the launch — `ShellExecuteW` followed immediately by
`app.exit(0)`, which Microsoft documents as needing `SEE_MASK_NOASYNC`. **It was
tested and it was wrong:** eight of eight `ShellExecuteW` calls followed by an
immediate `ExitProcess` launched their target. It is written down here because a
plausible cause that survives into a release note as a fix is worse than no
explanation at all.

What the evidence actually showed:

- The whole path works on this machine and this network. `genpacks
  --check-update` and `--fetch-update`, run from the installed binary and again
  from a build compiled as if it were 1.18.0, both check, download, and verify
  against the published checksum without complaint.
- Therefore the failures are environmental, and the code turned every
  environmental problem into silence.

The cause is one loop. `get` read until `WinHttpQueryDataAvailable` or
`WinHttpReadData` returned an error and then broke out and returned `Ok` with
whatever had arrived — it could not tell the end of a response from the end of a
connection. A dropped connection was a successful download of a shorter file,
and the same loop serves the release JSON, `SHA256SUMS.txt` and the installer,
which is why one fault produced three unrelated-looking messages.

**The fix was confirmed live rather than assumed.** A temporary probe on the
real download printed `declared=11586368 received=11586368`, proving the
`Content-Length` header is being read and compared and that the new guard is not
inert. The probe was removed and the comparison extracted into `check_complete`,
which is unit-tested for the short, the over-long and the chunked cases.

## Not verified

- **An actual failing network.** Nothing here reproduced a dropped connection,
  a stalled proxy or an antivirus quarantine. The truncation guard is proven by
  a unit test over `check_complete` and by the live `Content-Length` probe; the
  timeouts, the retry schedule and the six-hourly pass are proven by
  construction and by their unit tests, not by having been seen to rescue a real
  failure. This is the central gap in this record.
- **The 1.19.0 → 1.20.0 update through the app's own UI.** Verified separately
  after publishing — see below — but at the time of writing this file the
  release did not yet exist to update to.
- **The new updater updating to something newer than itself.** By definition it
  cannot be exercised until 1.21.0 exists. What ran here is the *old* updater
  fetching this release; the rewritten one has been observed checking and
  reporting, not downloading a newer version.
- **The workflow guard.** `release.yml` now asks whether the tag already has a
  published release and skips the upload if so. The logic is three lines of
  shell and was not run in CI before tagging, because the only way to exercise it
  is to tag.
- **The full uninstall gate (`scripts/verify-uninstall.ps1`).** Not re-run. It
  needs a machine whose data can be discarded; this one holds 20 custom cursors
  and real user data. Nothing in this release touches the uninstall path.
- **ARM64 and 32-bit installers on real hardware.** Only PE machine types were
  checked, and only at 1.19.0 — the code for all three compiles and lints clean.
- **A machine with no WebView2 runtime**, **the Windows version guard's refusal
  path**, and **the §9 clean-VM gate** — all unchanged and still unexercised, for
  the reasons given in `v1.19.0.md`.

## Judgement calls

**Shipping a fix that its own audience cannot receive.** Anyone whose updater is
broken cannot be sent a working updater by that updater. The release notes lead
with this rather than burying it: 1.20.0 has to be installed by hand, and every
release after it repairs itself. The alternative — waiting until there is some
other delivery channel — leaves the bug in place indefinitely.

**The failed hypothesis is recorded.** See above. Testing it cost a few minutes
and it was wrong, which is the useful outcome; the fix that shipped is the one
the evidence pointed at.

**`ShellExecuteW` was replaced anyway.** It is not the cause, but the shell path
cannot report whether a process was created and the caller shuts the app down
immediately afterwards. `CreateProcess` gives a pid to log or an error to show.
Changed on its merits, not as a fix for this report.

**`CURSED_COMMIT` is unset in release builds**, so the log reads `local`.
Cosmetic, unchanged since 1.13.0, and visible in the launch line quoted above.
